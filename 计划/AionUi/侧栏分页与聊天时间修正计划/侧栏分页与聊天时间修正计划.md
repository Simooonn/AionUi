## 1.1 时间契约（唯一定义，每条都可测）

对每个会话计算 `chatActivityAt`，单位为毫秒：

1. **M**：满足下表“计入”条件的行中，最大的 `messages.created_at`。
2. **C**：取 `cli_updated_at`。只有以下条件全部成立时才有效：
   - `extra` 是合法 JSON；
   - `cli_session_id` 和 `cli_source` 都是非空字符串（trim 后判断）；
   - `cli_updated_at` 是数值，且不小于 `1e12`；
   - 还没有任何 id 以 `CLI_ROW_ID_PREFIX`（`'cli-'`）开头的行，即 CLI 历史尚未懒加载。
3. 取值规则：
   - C 有效时，取 `max(M ?? 0, C)`；
   - C 无效时，取 M；
   - 两者都没有时，取 `conversations.created_at`。
4. **永远不用** `conversations.updated_at`（即 `modified_at`）。原因：PATCH 会把它设为当前时间（`crates/aionui-conversation/src/service.rs:2349-2416`），ensure 和回填流程也会改它。

**C 的可靠性**

- C 只在创建导入会话时写入一次（`process/ace/importCliSessions.ts:176-187`）。之后重新扫描时会被去重跳过，所以置顶、改名、打开都不会改动它。
- Claude 的 C 取的是最后一条记录的时间（`parsers/claudeParser.ts:82`），可能是非聊天记录，因此会略晚于实际最后一条消息。
- Codex 的 C 取的是文件 mtime（`parsers/codexParser.ts:130`），只是近似值，见 R1。
- 懒加载完成后，以逐条记录的 M 为准。时间可能因此往回修正，但不会错误地往前跳。

**计入与不计入**

| 维度           | 计入                                                                   | 不计入                                                                                                                                                                                      |
| -------------- | ---------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| type（白名单） | `text`、`thinking`、`tool_call`、`tool_group`、`acp_tool_call`、`plan` | `tips`、`agent_status`、`permission`、`ask`、`acp_permission`、`acp_terminal_output`、`available_commands`，以及所有未知类型（类型清单见 `common/chat/chatLib.ts:424-437`、`:705-904`）     |
| hidden         | `= 0`                                                                  | 其他值。被替换的文本段（`stream_persistence.rs:306`）和 cron 隐藏提示（`aionui-cron/src/executor.rs:771`）都属于这一类。该列为 NOT NULL DEFAULT 0（`migrations/001_initial_schema.sql:99`） |
| created_at     | `typeof` 为 integer 或 real，且不小于 `1e12`；读出后 `Math.round`      | NULL、0、负数、秒级时间（`< 1e12`）、文本                                                                                                                                                   |

**补充约定**

- 消息时刻按消息创建时间计。upsert 时取 `MIN(旧, 新)`（`crates/aionui-db/src/repository/sqlite_conversation.rs:153`）。
- skill 和 cron 的产物存放在 `conversation_artifacts` 表，不参与计算。
- `cli-` 前缀是一份跨代码的契约，涉及三处：写入（`messageImporter.ts:262-263`、`:281`）、去重与清理（`:323`、`:364`）、回填（`aioncoreSchema.ts:252`）。三处共用同一个常量，并由契约测试守住。
- tie-break 规则：
  - 会话：`chatActivityAt` 降序 → `created_at` 降序 → `id` 升序；
  - 项目：时间降序 → `workspace` 升序。

SQL 只做一次全表查询。每处 `json_extract` 都先经过 `json_valid` 判断，这样脏 JSON 只影响它所在的那一行：

```sql
SELECT c.id AS id, c.created_at AS created_at,
  (SELECT MAX(m.created_at) FROM messages m
    WHERE m.conversation_id = c.id AND m.hidden = 0
      AND m.type IN ('text','thinking','tool_call','tool_group','acp_tool_call','plan')
      AND typeof(m.created_at) IN ('integer','real') AND m.created_at >= 1000000000000) AS msg_at,
  CASE WHEN json_valid(c.extra)
        AND json_type(c.extra,'$.cli_session_id') = 'text' AND length(trim(json_extract(c.extra,'$.cli_session_id'))) > 0
        AND json_type(c.extra,'$.cli_source') = 'text' AND length(trim(json_extract(c.extra,'$.cli_source'))) > 0
        AND json_type(c.extra,'$.cli_updated_at') IN ('integer','real')
        AND json_extract(c.extra,'$.cli_updated_at') >= 1000000000000
        AND NOT EXISTS (SELECT 1 FROM messages x WHERE x.conversation_id = c.id AND x.id LIKE 'cli-%')
       THEN json_extract(c.extra,'$.cli_updated_at') END AS cli_at
FROM conversations c
```

## 1.3 渲染端加载链与状态（待办 2）

**现状**：`ConversationHistoryContext.tsx:24-30` → `hooks/useConversationListSync.ts:350-391` 的 `refreshConversations` → `getUserConversations`（`common/adapter/ipcBridge.ts:1388`）。它只发一次请求，`limit=10000`，并且忽略 `has_more`。侧栏没有使用 `/api/sidebar`（`common/adapter/sidebarMapper.ts`）。

**列表读取 `loadAllConversations()`**

后端事实：

- limit 不做上限钳制（`crates/aionui-db/src/repository/conversation.rs:409-411`）。
- 分页是 `(updated_at, id)` 的 keyset，每页多取 1 条来判断 `has_more`（`sqlite_conversation.rs:434-470`）。
- 响应只有 `items`、`total`、`has_more`，**没有快照令牌**（`crates/aionui-common/src/pagination.rs:5-9`、`crates/aionui-api-types/src/conversation.rs:353`）。
- `cursor` 已经贯通到前端（`conversation.rs:267-273`、`ipcBridge.ts:1388-1396`、`apiModelMapper.ts:116-125`）。

一致性边界：

- **单页**（首页 `has_more = false`）：这一页由一条 `SELECT ... LIMIT n+1` 得到，是同一个语句的一致读，可以作为 `ok` 的前提。
- **多页**：没有快照令牌，无法检测“归档 A、同时新增 B”这类数量相等的替换。即使去重后的条数等于 `total`，也不能证明列表完整。因此多页只做 best-effort：
  - 循环翻页，最多 20 页；遇到空页但 `has_more` 仍为真，或 cursor 重复，立即停止；
  - 对可重试的 cursor 请求只做有限重读：同一 cursor 最多重读 1 次，整个刷新仍受 20 页上限约束；重读不能把多页结果提升为 `ok`；
  - 结果按 id 去重；
  - 状态**一律为 `'truncated'`，永远不会是 `ok`**。这表示无法证明同一快照，不表示已定位到具体漏项。
- 执行前用 §2.4 确认活跃会话数不超过 10000，让验收落在单页范围内。用户已在 Q4 确认超限的完整支持另做，当前须显式提示不完整并禁止据此清理置顶；本期不承诺多页强一致。若后续需要强一致，必须另行改后端增加 snapshot token，不纳入本期。

**翻页失败与刷新代次**

- 每一代刷新在本地累积列表页、去重结果和 `has_more`/停止原因；只在该代的列表、时间覆盖校验全部完成后，由一次原子发布提交 `conversation_idsState`、列表数据与 `activityStatus`。
- 翻页过程出现请求 reject、空页异常、cursor 重复或达到 20 页上限时，已收集的结果可发布但 `activityStatus = 'truncated'`（若根本没有可用列表则按状态表的 `'unavailable'` 处理）；任何情况下都不能标 `ok`。
- 新一代刷新开始后，旧代即使稍后完成也整代丢弃，不得覆盖新代。

**时间读取与覆盖校验**

- 列表成功后，再**串行**调用 `window.electronAPI.conversationActivityTimes?.()`。
- 列表中的每个 id 都必须在返回的 `times` 里。有缺项时，只重试 1 次时间读取。
- 两次读取之间的变化这样处理：
  - 期间新建的会话，`times` 里多出来，忽略；
  - 期间删除的会话，`times` 里缺失，记为 `unavailable`；随后的 `listChanged(deleted)` 会触发新一代刷新来恢复。
- 缺少时间映射的 id 不能进入 `ok`；重试仍缺时保留该 id 的上一代值，若从未有值则回退 `getActivityTime`，并把整代标为 `unavailable`。

**按刷新代次原子发布**

- 模块级的 `refreshSeq` 每次刷新加 1。
- 列表、时间、`conversation_idsState`、`activityStatus` 在同一代里一次性 `emitStoreChange` 发布。
- 返回时如果序号已经过期，就整代丢弃，不发布。

**`activityStatus` 状态表**

状态只描述最近一次**完整发布的刷新代次**；刷新正在进行时保留上一代已发布状态，首次刷新前为 `'pending'`。只有 `ok` 计入验收。保留旧值和回退只出现在非 `ok` 的状态里；任何列表缺项、时间映射缺项、翻页不确定性或数据漂移都不能标 `ok`。每次状态切换时，用 `writeRendererLog` 记一次日志。导出 `getConversationActivityStatus()` 供测试使用。

| 场景                                                            | 发布什么                                         | activityStatus  | `chat_activity_at`                                     |
| --------------------------------------------------------------- | ------------------------------------------------ | --------------- | ------------------------------------------------------ |
| 尚未完成首次刷新                                                | —                                                | `'pending'`     | —                                                      |
| 首页/列表请求失败，且没有可发布的完整列表                       | 沿用现有失败路径（`:374-381`），不替换上一代列表 | `'unavailable'` | 保留上一代已知值；无旧值的行不发布                     |
| 多页在中途请求失败，但已有可用页                                | 已收集的去重列表                                 | `'truncated'`   | 读到的新值；未覆盖 id 按故障态缺项处理                 |
| 时间 IPC 不存在、reject 或返回 `ok:false`                       | 新列表                                           | `'unavailable'` | 已知 id 保留上一代的值；新 id 回退到 `getActivityTime` |

````bash

: "${AIONUI_PROD_DB:?Set the verified existing prod database path}"
python3 -I - "$AIONUI_DEV_DB" "$AIONUI_PROD_DB" <<'PY'
from pathlib import Path
import sqlite3
import sys
from time import perf_counter

plan = Path('计划/AionUi/侧栏分页与聊天时间修正计划/侧栏分页与聊天时间修正计划.md').read_text()
query = plan.split('```sql\n', 1)[1].split('\n```', 1)[0]
for supplied_path in sys.argv[1:]:
    path = Path(supplied_path).expanduser().resolve(strict=True)
    if not path.is_file():
        raise SystemExit(f'STOP: not a database file: {path}')
    connection = sqlite3.connect(path.as_uri() + '?mode=ro', uri=True, timeout=1.0)
    try:
        connection.execute('PRAGMA query_only=ON')
        connection.execute('BEGIN')
        journal = connection.execute('PRAGMA journal_mode').fetchone()[0]
        active = connection.execute('SELECT COUNT(*) FROM conversations WHERE archived_at IS NULL').fetchone()[0]
        messages = connection.execute('SELECT COUNT(*) FROM messages').fetchone()[0]
        wal = Path(str(path) + '-wal')
        print({'db': str(path), 'journal_mode': journal, 'wal_bytes': wal.stat().st_size if wal.exists() else 0, 'active': active, 'messages': messages})
        for row in connection.execute('EXPLAIN QUERY PLAN ' + query):
            print(row)
        started = perf_counter()
        rows = connection.execute(query).fetchall()
        elapsed_ms = (perf_counter() - started) * 1000
        print({'rows': len(rows), 'elapsed_ms': elapsed_ms})
        if active > 10000:
            raise SystemExit('STOP: active conversations exceed the agreed 10000 scope; report incomplete data')
        if elapsed_ms >= 50:
            raise SystemExit('STOP: query exceeds the budget; resolve R5 before continuing')
    finally:
        connection.close()
PY
````

# 附录三：RALPLAN-DR（模式 SHORT）

## 原则

1. **持久证据优先**：时间能从数据库重复推导出来，不靠冻结缓存。
2. **最小改动面**：不跨仓库，不替换 backend，不改变导入器的写入行为。
3. **不改写历史数据**。
4. **统一可见性契约**：渲染、Ctrl+Tab、定位共用同一组谓词。
5. **失败要显式**：故障态和尽力而为的结果都可以观测，且不能算作验收通过。

## 主要驱动

1. 正确性：AC4、AC6、AC7 都要成立。
2. 部署风险：aioncore 是本地 fork 构建，替换它需要重新出包。
3. 性能：每次刷新只查一次时间。

## 选项

### A．AionUi 主进程只读派生时间，通过独立 IPC 批量返回（候选方案）

优点：

- 只改一个仓库，不替换 backend；
- 能纠正历史上被污染的 `modified_at`；
- 复用现有模式（`sessionFiles.ts:189`、`aioncoreSchema.ts:46`）。

缺点：

- 与 aioncore 的私有 schema 耦合；
- 多一次 IPC；
- Web 宿主没有这个能力（Q1）；
- 列表多页时没有快照，只能尽力而为（Q4）；
- 已有的 `Date.now()` 行无法纠正（Q3）。

### B．AionCore 的列表响应增加一个由查询派生的 `last_message_at`

做法：在列表 SQL（`sqlite_conversation.rs:434-470`）中，按 §1.1 的同一口径加一个相关子查询，经 `convert.rs:92` 输出。不需要冗余列和迁移，也不需要改 PATCH。

优点：

- 数据源权威，Web 宿主也能用；
- AionUi 不新增私有耦合；
- 后端还可以顺带提供单次全量或快照，消除多页的限制。

缺点：

- 需要改 fork、重建、替换 bundled backend，并持续维护与上游的差异；
- C 规则需要在 Rust 侧读取 AionUi 写入 extra 的字段（`importCliSessions.ts:176-187`），形成跨仓库的语义耦合。

如果 Web 是硬需求，或多页必须强一致，B 是更合适的选择，但这与“不改 AionCore”的边界冲突，需要用户决定（Q1、Q4）。

### C．UI 层冻结或缓存时间（淘汰）

历史污染无法恢复，重启后也会失效。AC7 明确禁止这种做法。

### D．回写修正 `updated_at`（淘汰）

需要和 AionCore 争抢同一列（`aioncoreSchema.ts:216-218`），而且会改写历史数据。

## 已采用方案（2026-10-19 获批实施）

依据 Q1、Q3、Q4 的明确回答及 Q2 的技术默认，用户另行选择 Ralph 实施后，采用 A 完成实现；未提交、未推送、未改写生产历史。

# 附录四：ADR（已获实施授权，实际结果见 §2.6）

- **Decision**
  - **已采用技术决策（2026-10-19）**：在已确认的桌面端、历史数据不改写及规模范围内，侧栏使用 AionUi 主进程只读派生的 `chat_activity_at`，契约见 §1.1。无法可靠取值的个别会话列明限制，不伪造通过。
  - 列表、完整标记和时间按刷新代次原子发布，只有“单页 + IPC ok + 全部覆盖 + 无漂移”时才算 `ok`；多页一律是 best-effort 并记为 `truncated`，不宣称强一致。只有完整且 `activityStatus = 'ok'` 时才允许 `pruneOrphans`，部分/截断列表不得改写置顶配置。

  - 导入器的写入行为不变；本期 AionCore 不改、不主动写库。
- **Drivers**：正确性、不替换 backend、单次批量查询、不扩大写入权限，以及必须显式暴露故障/尽力而为状态。
- **Alternatives considered**：B（AionCore 列表查询派生 `last_message_at`，公平比较查询派生字段并可后续提供 snapshot token）、C（UI 冻结）、D（回写 `updated_at`），比较见附录三。
- **Why chosen**：A 与已确认的桌面端、不改历史数据及规模边界相符，不需重新出包 backend。正常路径的 AC4–AC7 仍须测试与核查证明；无法可靠恢复的个别会话另列影响并单独确认，不宣称全部历史修复；Ralph 实施已于 2026-10-19 获明确授权。
- **Consequences**
  - 只有故障/尽力而为状态才对已有值保留、对从未拿到值的会话回退到 `getActivityTime`；`ok` 不允许含回退或缺项。
  - cron 和飞书沿用旧语义。
  - 新增一处与私有 schema 的耦合。
  - Q1 已确认仅修 Electron 桌面端，Web 宿主不纳入本次范围；平台确认不构成实施授权。
  - 无快照的多页只能 best-effort，`truncated` 不计入 AC4、AC7。
  - 历史导入行只核查、不覆盖；源文件缺失/不可读或时间不一致不主动重建。审计分为编码前只读 SQL/规模/WAL 的阶段 A，以及审计接缝/契约测试编码后、行为修改前逐行核查的阶段 B；阶段 B 阻断不能被“阶段 A 已通过”替代。
- **Follow-ups**
  - 如果需要支持 Web、强一致的多页，或多客户端，评估 B；强一致需要后端 snapshot token，不纳入本期。
  - 升级 aioncore 时，核对 type 和 hidden 的语义是否变化。
  - 用户已在 Q3 选择本次不改历史数据。未来如单独批准历史修正，先更新允许清单、备份/回滚方案、ADR 和测试；当前范围确认不能授权修改导入器重建历史。
