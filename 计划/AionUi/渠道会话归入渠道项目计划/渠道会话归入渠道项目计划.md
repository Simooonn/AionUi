## §3 建会话前准备目录 + 发送前自愈（步骤 4、5）

新增一个私有辅助函数，单独拿出来是为了能单测：

```rust
/// Ensures `<root>/<channel dir>` exists. Returns `None` (logged at warn) on failure so the
/// caller falls back to the per-conversation temp workspace instead of failing the reply.
async fn ensure_channel_workspace(root: &Path, platform: PluginType) -> Option<PathBuf> {
    let dir = root.join(channel_workspace_dir_name(platform));
    match tokio::fs::create_dir_all(&dir).await {
        Ok(()) => Some(dir),
        Err(err) => {
            warn!(platform = %platform, path = %dir.display(), error = %err,
                "channel workspace unavailable; falling back to a temp workspace");
            None
        }
    }
}
```

插入点在 `create_conversation_for_session` 里：`extra["model"]` 写完（:166-171）之后、`let req = CreateConversationRequest`（:173）之前。

```rust
if let Some(dir) = ensure_channel_workspace(&self.channel_workspace_root, platform).await {
    extra["workspace"] = serde_json::Value::String(dir.to_string_lossy().into_owned());
}
```

- 放在 settings 查询之后。这样前面的配置读取一旦失败就直接返回，不会白建目录。
- 路径不做 canonicalize，保留 `~/.aionui` 这个符号链接的写法，和现有临时目录的写法一致（库里现有的行就是 `/Users/wmm/.aionui/conversations/...`）。项目侧的 `canonical::to_file_uri` 会自己解析真实路径，basename 不变。
- `assistant_id` 有值的分支同样会带上 `extra`，所以两条分支都能生效，不用分开处理。
- 失败时回退，不报错。理由见附录五 ADR。

**发送前自愈（步骤 5）**

已绑定会话的 session 会跳过创建（`message_service.rs:62-67`），所以只在创建时建目录不够：渠道目录建好之后如果被删掉，`aionui-conversation/src/session_context.rs:157-173` 会拒绝不存在的非自动 workspace，冷启动 agent 时 warmup 失败，之后**每条** IM 消息都只回一句 `❌ Failed to process`（`orchestrator.rs:180-199`），直到用户点 New Session。

在 `send_to_agent` 里、拿到 `conversation_id` 之后、`warmup`（:89 附近）之前，无条件调用一次：

```rust
// Self-heal: bound sessions skip creation, so recreate the shared channel dir here in case it
// was deleted; otherwise warmup rejects the missing custom workspace on every message.
let _ = ensure_channel_workspace(&self.channel_workspace_root, platform).await;
```

- `create_dir_all` 幂等，目录已存在时只是一次 stat。创建路径上会和步骤 4 各调一次，可以接受。
- 失败时 `ensure_channel_workspace` 已经记了 warn，这里不改变流程：该报什么错还是由 warmup 报。
- 对 workspace 不是渠道目录的旧会话（比如 `75a1f876`），这一步只是多建一个空的渠道目录，没有副作用。
- 自愈只覆盖「agent 是冷的」情况。agent 进程还活着时，warmup 直接复用它（`service.rs:4679-4683`），它的 cwd 仍是被删掉的旧目录 inode；要等这个进程被回收或重启之后才完全恢复（附录三）。

# 附录四：RALPLAN-DR 摘要

**模式**：SHORT（普通功能改动，有回滚路径，没有数据迁移）。

**原则**

1. 复用现有行为：会话服务和项目服务对「用户自选目录」的处理已经满足需求，只在渠道层补上缺失的输入。
2. fork 差异越小越好：只改 `aionui-channel`，外加 `aionui-app` 的 1 行接线，方便以后 rebase 到上游。
3. 渠道回复的可用性优先于归组：目录出问题时不能让机器人不回话。
4. 漏改要在编译期暴露：目录名映射穷举所有变体。

**决策驱动（前三）**

1. 侧栏按 `extra.workspace` 分组，不看 `project_id`（附录二）。所以必须改 workspace，只改项目绑定没用。
2. 零配置、前端不改、只改 AionCore fork（spec 约束）。
3. `source` 分不出 Lark 和 LarkIntl、Slack 和 Discord，只有渠道层手里有准确的 `PluginType`。

**可选方案**

| 方案                                                                                                                     | 优点                                                                                            | 缺点                                                                                                                                                                                                                                                                                                                                    |
| ------------------------------------------------------------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **A（选定）** 渠道层算出 `<work_dir>/channels/<Name>`，先建目录，再写入 `extra.workspace`；`work_dir` 由构造函数显式注入 | 改动最小；会话、项目、删除、前端都沿用现有逻辑；`PluginType` 精确；依赖在签名上可见             | 构造函数要多一个参数，改 6 处调用                                                                                                                                                                                                                                                                                                       |
| A' 同 A，但不加参数，改为给 `ConversationService` 加 `workspace_root()` getter，渠道层从它取根目录                       | `ChannelMessageService::new` 签名不变，`state.rs` 和 5 处测试调用点都不用动；两边根目录天然一致 | 现有 5 个测试用 `std::env::temp_dir()` 构造 `ConversationService`（附录二），用 getter 后渠道测试会在共享的 `/tmp/channels` 下建目录、互相污染；要避免污染就得照样逐个改这 5 个测试，A' 实际只省下 `state.rs` 的 1 行和 5 个实参；还要在 conversation crate 新增公开 API，fork 差异多一个 crate；依赖藏在别的服务内部，不如显式注入直观 |

- C 保留临时目录，只把 `project_id` 绑到渠道项目：侧栏不看 `project_id`，做完界面上没有任何变化（spec Round 4 前提作废的原因）。
- D 前端按 `source` 分组：违反「前端不改」，而且 `source` 分不出渠道。
- E 在渠道配置里加目录设置项：违反零配置。

# 附录五：ADR

- **Decision**：
  - 在 `ChannelMessageService::create_conversation_for_session` 里，按 `PluginType` 穷举映射出固定的 ASCII 目录名，先 `create_dir_all(<work_dir>/channels/<Name>)`，再写入 `extra.workspace`。项目归属、删除保护、前端分组全部沿用现有逻辑。
  - 目录创建失败时记 warn、不写入 workspace，退回每条会话一个临时目录的旧行为。
  - 每次 `send_to_agent` 在 warmup 前再幂等地确保一次目录存在，让 agent 已冷的已绑定 session 在目录被删后自愈（agent 还活着时的限制见附录三）。
- **Drivers**：侧栏按工作目录分组；零配置、前端不改、只改 fork；只有渠道层知道准确的渠道类型。
- **Alternatives considered**：
  - A'：给 `ConversationService` 加 `workspace_root()` getter，不改构造函数；
  - B：渠道层传专用 extra 键，由会话服务算目录；
  - C：只绑定 `project_id`；
  - D：前端按 `source` 分组；
  - E：做成配置项；
  - 失败处理的另一种做法：硬失败，直接返回错误。
  - 否决理由见附录四。硬失败被否决的理由：`ConversationService::create` 对不存在的目录会返回 `WorkspacePathUnavailable`，IM 用户就收不到任何回复；而归组只是展示层的便利。回退后的代价只是这条会话落在「对话」里，日志可查。
- **Why chosen**：方案 A 只给现有逻辑补上缺的那一个输入。可以证明会话服务和项目服务对自选目录的处理已经满足 AC1–AC4（附录二），改动集中在一个 crate，rebase 成本最低。
- **Consequences**：
  - 同一渠道的会话共享 cwd：文件可能互相覆盖；Claude Code 的会话记录和项目级 memory 也会落到同一个 cwd 下（用户已接受）。
  - **信任边界变宽**：渠道会话以 yolo 运行，该渠道任何已配对的用户（私聊或群聊）都能让 agent 在共享目录写下 `CLAUDE.md`、`.claude/skills/*` 或 cwd 级 memory，内容留在目录里，之后该渠道所有会话都会自动加载，构成持久化的提示注入入口。未配对的用户只拿到配对码。缓解：写进 `ACE_CHANGES.md` 并告知用户，目录保持可检查。
  - 按 cwd 共享的状态会串到一起：快照「变更 / 丢弃」面板、Antigravity 审批 hook、cron skill-suggest 文件（附录三）。
  - 渠道目录永不自动删除；被手动删掉后，下一条消息会重建目录，但仍在运行的 agent 要等回收或重启后才完全恢复。
  - 旧会话 `75a1f876` 留在「对话」里。
  - 飞书显示为 `Lark`。
  - 正式版同时带上 `77fdeb09`。
  - `ChannelMessageService::new` 的签名变了，以后合并上游时要留意冲突。
- **Follow-ups**：
  1. 飞书目录是否改成别的名字（例如 `Feishu`），由用户决定。
  2. 如果共享目录真的出现文件互相覆盖，或者信任边界成了实际问题，再评估按聊天细分子目录。前提是前端允许按 `project_id` 分组（那时每个聊天一个子目录也能归进同一个渠道项目）；否则会和「一个渠道一个项目」冲突，需要重新确认。
  3. 下次把 fork rebase 到新的上游 tag 时，带上本 commit，重新核对 6 个调用点和 `service.rs` 的 workspace 分支。
  4. `/Applications` 包里 npm 等符号链接失效的老问题（附录三），这次不处理。
