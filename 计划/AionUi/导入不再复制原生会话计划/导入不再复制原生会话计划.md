# 附录一：方案是什么

## §0 根因与目标（一段话）

原生会话（在 AionUi 里新建）的 CLI 会话 id 只登记在 aioncore 的 `acp_session.session_id`，而导入基线 `readImportedCliSessionIds`（`aioncoreSchema.ts:97-105`）只读 `conversations.extra.cli_session_id`。原生会话选了真实项目目录作工作区时，Claude 的 jsonl 落在 `~/.claude/projects/<项目>/`，不被 `isAionUiInternalWorkspace`（`importCliSessions.ts:187-198`）排除，于是被当成终端会话导入，生成与原生会话共用同一 Claude 会话的副本。目标：基线并入 `acp_session` 全部文本 sid（含孤儿行——你在 Round 1 与 2026-10-14 两次确认"删了就不回来"）；导入末尾既有的重复清理（`importCliSessions.ts:246-284`）扩展到"导入副本 vs 仍存在的原生会话"，原生会话恒为保留方，保护规则（App 内消息 / cron / 打开的终端）与删除通道不变。

   ```ts
   /**
    * Every CLI session id aioncore currently points a conversation at (native or
    * resumed import), ORPHAN rows included. acp_session.session_id is a CURRENT
    * resume pointer, not a ledger: aioncore rewrites and clears it in place. Orphan
    * rows survive only because aioncore's conversation delete removes the row
    * first and its acp_session delete then matches nothing.
    */
   export const ACP_SESSION_IDS_SQL = `SELECT session_id AS sid
     FROM acp_session
     WHERE typeof(session_id) = 'text'

     return new Set(rows.map((r) => r.sid));
   ```

5. `:118-142` `DUPLICATE_IMPORT_LOSERS_SQL` 改为 CTE（JSDoc 同步：保留方优先级 = 通过 `acp_session` 认领该 sid 的**非导入**会话 → 最早导入（`created_at`, `rowid`）；淘汰方只能是导入行）：

   ```sql
   WITH claims AS (
     -- Imported rows claim their cli_session_id (fork copies excluded, as before).
     SELECT c.id, c.user_id, c.archived_at, c.created_at, c.rowid AS rid,
            json_extract(c.extra, '$.cli_session_id') AS sid, 1 AS imported
       FROM conversations c
      WHERE json_type(c.extra, '$.cli_session_id') = 'text'
        AND json_extract(c.extra, '$.cli_session_id') <> ''
        AND json_extract(c.extra, '$.fork') IS NULL
     UNION ALL
     -- Non-imported rows claim the session aioncore points them at. The JOIN drops
     -- orphan acp_session rows (nothing left to protect); the json_type guard drops
     -- every imported conversation's own acp_session row, so an import never claims
     -- for itself even after aioncore re-points it.
     SELECT c.id, c.user_id, c.archived_at, c.created_at, c.rowid,
            a.session_id, 0
       FROM acp_session a
       JOIN conversations c ON c.id = a.conversation_id
      WHERE typeof(a.session_id) = 'text'
        AND a.session_id <> ''
        AND json_type(c.extra, '$.cli_session_id') IS NOT 'text'
   )
   SELECT r.id, r.sid AS cliSessionId,
          (r.archived_at IS NOT NULL) AS archived,
          EXISTS (SELECT 1 FROM messages m WHERE m.conversation_id = r.id AND m.id NOT LIKE 'cli-%') AS hasLiveTurns,
          EXISTS (SELECT 1 FROM cron_jobs j WHERE j.conversation_id = r.id) AS hasCronJobs
     FROM (
       SELECT claims.*,
              ROW_NUMBER() OVER (
                PARTITION BY user_id, sid
                ORDER BY imported ASC, created_at ASC, rid ASC
              ) AS rn
         FROM claims
     ) AS r
    WHERE r.rn > 1
      AND r.imported = 1
    ORDER BY r.user_id, r.sid, r.rn
   ```

   - 无 `acp_session` 行时，`claims` 只剩导入分支，结果与现行 SQL 完全一致（既有用例原样通过即为证明）。
   - 损坏的 `extra` JSON：基线的 `IMPORTED_CLI_SESSION_IDS_SQL` 先抛 `query-failed` 中止导入，清理不会运行（既有 `aceImportDedupe.test.ts:303-310`）——语义不变。
   - `DuplicateImportLoser` 类型与 `findDuplicateImportLosers`（`:144-160`）的映射不变。
   - 已在正式库快照上只读试跑（两位评审各自复跑一致）：输出恰为附录二表中 12 个导入副本，原生会话 0 条。

## §4 aioncore 删除会话的行为（本地源码 `~/wmm-code/ace-diy/AionCore`，分支 fix/pending-ask-keepalive）

- `ConversationService::delete`（`crates/aionui-conversation/src/service.rs:2593-2680`）：标记删除 → 删除钩子（`task_manager.rs:394-403` 只按 conversation_id 杀该会话自己的 agent 进程；cron 钩子 `aionui-cron/src/service.rs:2111`；侧栏排序钩子 `aionui-sidebar/src/cascade.rs:34`）→ 删会话行（消息级联）→ `delete_for_user`（空操作）→ 只删 `<root>/conversations/*-temp-<id>` 形态的自动工作区（`:5143-5173`）。`close_session`（`aionui-ai-agent/src/protocol/acp.rs:325`）全仓无调用方，删除不会向 Claude 发 session/close。

# 附录三：RALPLAN-DR / 风险 / ADR

## 原则（Principles）

1. "AionUi 已拥有"以 aioncore 自己的绑定记录 `acp_session` 为准，同一条 SQL 适用于所有来源（Claude 已实证；Codex / Gemini / opencode 为推断，不一致时退回现状、不误删）。
2. 名单失真时宁可中止：新信号不得掩盖旧绊线（绊线只看已导入部分）。
3. 删除只删导入副本；原生会话永远是保留方；删除通道与保护规则沿用已经 e2e 验证过的既有路径。
4. 最小改动：不改 parser、不改渲染层 / i18n、不扩共享闸门、不新增源码 / 测试文件。
5. 真实数据用独立对照验证，不写死数量。

## 决策驱动（Decision Drivers，前 3）

1. 真实数据正确：12 对重复、你仍在副本里续聊（受保护数在增长），修复越早，能自动清掉的越多。
2. 破坏性清理的安全：副本与原生共用一个 Claude 会话，jsonl 绝不能动；原生会话绝不能进淘汰名单。
3. 对 aioncore 漂移可观测：schema 变化显式失败；指针语义与孤儿行现状有运行时日志、探针与升级核对项。

## Pre-mortem（5 个失败场景）

1. **孤儿行消失**：上游修好 `delete_for_user` 的顺序（`service.rs:2656` 注释即本意），或某次迁移一次性清扫孤儿行（`migrate_repair.rs:258` 有先例）→ 已删的原生会话（及点开过又删掉的导入会话）在下次导入时作为导入会话成批回来。缓解：§4.7 升级核对 (1) 防清扫（孤儿文本 sid 数不得下降）、(2) 防修序（读源码核对删除顺序与 `EXISTS` 守卫）；ADR Follow-up 1。实际暴露面小：UI 删除原生会话本就 unlink 其 jsonl。
2. **指针被改/清空**：原生会话遇 dead anchor / SessionNotFound 恢复（`session_agent.rs:1369`、`:3495`，`acp_error_recovery.rs:259`）或团队清上下文（`service.rs:2584`）→ 旧 sid 脱离名单，旧 jsonl 被导入为副本，且清理关联不到（永久副本）。缓解：`verify.sh` 的 `sdk-cli` 覆盖探针 + §4.7 升级核对 (3)；运行时 `[ace:import] baseline` 日志；ADR Follow-up 1。
3. **清理 SQL 误判导致删错**：自我认领、孤儿行、fork 让导入会话被错判。缓解：认领分支要求会话仍存在且非导入；§3.5 七类夹具；上线前 `verify.sh` 对照相等；保护规则不变；快照取证。
4. **绊线被掩盖**：`extra` 语义漂移使"已导入"读成空、`acp_session` 非空 → 并集非空跳过绊线 → 再现 379 条重复。缓解：绊线只看已导入部分（§2.3）；§3.3d 钉住。
5. **手动删受保护副本时删掉了共用 jsonl**：你在侧栏或归档页删除副本 → `deleteConversationsWithFiles`（`useConversationActions.ts:162`）按副本的 `cli_session_id` 解析到原生会话共用的 jsonl（`sessionFiles.ts:84-87`）并 `rmSync`（`:282`）→ 原生会话下次 resume 失败、Claude 侧上下文永久丢失，无提示。（反过来删原生会话也会删掉副本依赖的同一文件。）缓解：§7.4 只走后端删除端点或只归档；`verify.sh` 清单表头固定警告；你按清单逐条点名、执行人删前删后 `shasum` 比对；根治见 ADR Follow-up 3。

## ADR

- **Decision**：采用方案 A。导入基线 = 已导入 sid ∪ `acp_session` 全部文本 sid（含孤儿行）；绊线只看已导入部分；重复清理按 `(user_id, sid)` 分区，非导入认领者优先于任何导入行，淘汰方只限导入行，保护规则与删除通道不变。
- **Drivers**：真实数据正确、破坏性清理安全、对 aioncore 漂移可观测。
- **Alternatives considered**：B（加 Claude `entrypoint` 兜底）、C（只用标记）、D（给原生会话写 `cli_session_id`）、E（一次性清理脚本）、F（AionUi 侧 sid 台账）。
- **Why chosen**：A 用 aioncore 自身的绑定事实，一处改动同时覆盖防再犯与清存量；B 目前 0 例可多抓、会误伤 `claude -p`，且你在 2026-10-14 选择不做；C 无法独立完成清理；D 破坏"导入会话"标识语义；E 违反"不直写正式库"；F 新增持久状态而当前 0 例可多抓。
- **Consequences**：
  - 导入会话只要在 AionUi 里**点开过**、之后被删除，以后不会再导回（你于 2026-10-14 确认；正式库已有 15 条导入会话属于此类）。通过 UI 删除时 jsonl 通常已被一并删除，这条附带影响多数情况下本来就不会被触发。
  - 原生会话若在终端里用 `claude --resume` 续写，续写内容不会以任何形式出现在 AionUi（其 sid 已在名单中；原生会话也不做 jsonl 懒同步）。
  - "删了不回来"依赖上游孤儿行现状；被 aioncore 改指/清空的旧 sid 会漏网（均有探针与升级核对）。
  - `acp_session` 成为导入的硬依赖：该表漂移时整个导入中止（宁可不导，不制造重复）。
- **Follow-ups**：1）若探针非 0 或升级核对 (1) 数值下降：补方案 B，但只用于"`sdk-cli` 且不在基线"的 Claude 会话；或在 AionUi 侧维护只追加的 sid 台账；2）上游 `delete_for_user` 空操作是独立 bug，修与不修都需同步本计划核对项；3）**本地文件删除的共享守卫**（需你确认后另行立项）：`resolveSessionFilePath`（`sessionFiles.ts:69-110`）在该 sid 仍被其他存活会话引用（`extra.cli_session_id` 或 `acp_session.session_id`）时不返回文件路径，让 UI 删除对共用会话安全；同一陷阱也存在于导入会话的 fork（fork 原样复制父会话的 `cli_session_id`，`service.rs:2851-2866`）；4）"两条会话共用一个 Claude 会话"的续聊防护（例如在副本里发消息前提示）另行立项。
