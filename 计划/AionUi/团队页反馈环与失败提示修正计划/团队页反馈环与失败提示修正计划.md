# 附录一：方案

## RALPLAN-DR 摘要（short 模式）

### Principles（原则）

1. **依赖只取真正用到的值**：effect，以及会传进 effect 的回调，只依赖稳定原语或稳定函数。不依赖整个 context 对象，也不依赖整个 port 对象。
2. **身份跟着内容走**：派生值在内容不变时保持身份；内容变化时必须换身份，依赖它的 UI 才能重渲染。
3. **用户可见行为最小变化**：只静默团队模式下挂载预热失败的 toast。发送时、单聊不变。恢复后斜杠命令照常可用。不新增自动重试。
4. **只改前端**：不动 aioncore。
5. **修复要被测试抓住**：每个修复至少有一条“撤掉修复后断言失败”的测试。

### Decision Drivers（前 3 项）

1. 打断失败死循环，并消除正常运行时的放大，包括 dormant 成员懒唤醒时（AC1–AC3、AC6）。
2. pill 阻塞状态不过期（AC10）；失败后恢复，斜杠命令可用（AC9）；不引入自动重试。
3. 改动面可控、可单测、不违反目录规模的 ratchet 规则。

### S1 拆分 port，暴露 `sessionReady`（`pages/team/hooks/TeamPermissionContext.tsx`）

做法：

1. 基础 port 只随 team 变：
   ```ts
   basePort = useMemo(

     [team_id, warmupSession]
   );
   ```
   这里不传 `isConfigOptionBlocked`；它在 `teamConfigOptions.ts:29` 本来就是可选参数。
2. 集合按内容稳定：
   ```ts
   const runtimeStartingKey = [...runtimeStartingConversationIds].sort().join('\n');
   const stableRuntimeStartingIds = useMemo(
     () => new Set(runtimeStartingKey ? runtimeStartingKey.split('\n') : []),
     [runtimeStartingKey]
   );
   ```
   conversation id 是短 hex 串，不含换行。
3. 对外的 port：
   ```ts
   configOptionsPort = useMemo(
     () => ({ ...basePort, isConfigOptionBlocked: /* 原 :75-77 的规则，改读 stableRuntimeStartingIds */ }),
     [basePort, stableRuntimeStartingIds, leaderConversationId]
   )
   ```
   展开时复制的是函数引用，所以 `load` 等保持不变。
4. 新增 prop 和 context 字段 `sessionReady: boolean`：类型加在 `:5-20`，并加入 `value` 的 `useMemo` 依赖（`:82-93`）。

不新增文件。`hooks/` 目录已有 14 个子项。

### S3 `AionrsSendBox`（`pages/conversation/platforms/aionrs/AionrsSendBox.tsx`）

现状：

- `prepareRuntimeConfig`（`:171-173`）和 `prepareRuntimeSync`（`:174-180`）都依赖整个 `teamPermission`。
- 挂载 effect（`:196-206`）依赖 `prepareRuntimeSync`。
- `useSlashCommands`（`:208-212`）也拿 `prepareRuntimeSync` 当 `prepareRuntime`。`useSlashCommands.ts:111` 的 effect 依赖它，并在 agent 就绪后（`:75`）于 `:84` 调用它。
- `executeCommand` 的依赖（`:323`）是整个 `teamPermission`。

做法：

1. 在文件顶层定义 `const noopPrepareRuntime = async (): Promise<void> => {};`，替换 `prepareRuntimeConfig`。原函数在两个分支里都不做任何事。
2. 定义：
   ```ts
   const isTeamMode = Boolean(teamPermission);
   const teamWarmupSession = teamPermission?.warmupSession;
   const teamSessionReady = teamPermission?.sessionReady ?? false;
   ```
3. `prepareRuntimeSync` 改为调用 `teamWarmupSession`，依赖改为 `[conversation_id, teamWarmupSession]`。`warmupSession` 本身是稳定的，见 `TeamPermissionContext.tsx:51-64`。
4. 挂载 effect：
   - 依赖改为 `[conversation_id, isTeamMode, prepareRuntimeSync, t]`，**不含** `teamSessionReady`。
   - 增加 `cancelled` 标志，防止过期的 `.then(setAgentWarmed(true))` 生效。
   - catch 分支：团队模式下改为 `console.warn('[AionrsSendBox] team mount warmup failed', error)`，不再调用 `Message.error`；单聊保持原样。
5. 新增“恢复预热”effect，只在“挂载之后观察到 `sessionReady` 从 false 变为 true，且本成员尚未预热”时触发一次：
   ```ts
   const prevSessionReadyRef = useRef(teamSessionReady);
   useEffect(() => {
     const wasReady = prevSessionReadyRef.current;
     prevSessionReadyRef.current = teamSessionReady;
     if (!isTeamMode || wasReady || !teamSessionReady || agentWarmed) return;
     let cancelled = false;
     void prepareRuntimeSync()
       .then(() => {
         if (!cancelled) setAgentWarmed(true);
       })
       .catch((error) => console.warn('[AionrsSendBox] team recovery warmup failed', error));
     return () => {
       cancelled = true;
     };
   }, [isTeamMode, teamSessionReady, agentWarmed, prepareRuntimeSync]);
   ```
   行为分析：
   - 下降沿不做任何事，所以不会自动重试。
   - 已预热时不做任何事，所以健康冷启动时 phase 抖动不会多打请求。
   - 若挂载预热仍在进行，`warmupSession` 的进行中去重（`TeamPermissionContext.tsx:52-54`）会复用同一个 promise。
   - 一次失败的尝试不会改变任何依赖，因此不会自激。
6. `executeCommand` 做两处改动：
   - 删掉 `:256` 的 `if (teamPermission) await teamPermission.warmupSession();`，改成在 `try`（`:265`）里第一行写 `if (teamWarmupSession) await teamWarmupSession();`。这样 warmup 失败会进入 catch，走 `markSendFailed` + `Message.error`，和 ACP（`AcpSendBox.tsx:327`）一致。
   - `:323` 依赖里的 `teamPermission` 换成 `teamWarmupSession`。

   副作用：“未选模型”的检查（`:257-260`）原来排在 warmup 后面，现在排到了前面。没选模型时会先弹出警告，不再白跑一次 warmup。

# 附录二：验收标准

## 相对 spec 的细化（待办 0，需用户确认）

- **spec AC1**：“挂载阶段固定次数”改为下文 AC1 的硬上限。原因是 ACP 成员也会在挂载时预热（`AcpChat.tsx:75-77` → `useAcpMessage.ts:684-716`），但所有成员共用 `warmupPromiseRef` 做进行中去重。
- **spec AC2**：“每成员 ≤ 2”改为“挂载期 ≤ 5N，稳态为 0”。原因见附录四：每个 ACP 成员最多有 5 个实例，`fetchConfigOptionsOnce` 只合并进行中的请求，挂载期的精确次数取决于时序。
- **spec AC7**：Aion CLI 发送时的 warmup 在 `try` 之外（`AionrsSendBox.tsx:256` 对 `:265`），失败会被 `SendBox/index.tsx:1622-1628` 吞掉，**今天就是静默的**，输入也会被清空。这与第 3 轮选项中“点了发送却失败，必须给反馈”的前提不符。2026-10-21 用户决定这次一起修，这一条覆盖 spec 中“不改发送时失败提示”的非目标，仅对 Aion CLI 生效。

## 定义

- 进入团队页时，由 CDP 脚本打印墙钟时间 `t0`。
- 挂载期：`[t0, t0+10s)`；稳态期：`[t0+10s, t0+30s]`。
- `N`：成员数。
- 计数方法见附录三 V3。
- 失败场景的团队：**leader 是 Aion CLI（`model: 'default'`），另有至少 1 个 ACP 成员**，全新创建且未发送任何消息。

## 验收条目

# 附录四：依据与证据

## 反馈环链路

1. 挂载 effect（`AionrsSendBox.tsx:196-206`）和 `useSlashCommands.ts:84/111` 经 `prepareRuntimeSync` 调用 `warmupSession`，即 `POST /api/teams/:id/session`。
2. 返回 409 `TEAM_MEMBER_RUNTIME_FAILED` 后，`AionrsSendBox.tsx:203-204` 用 `Message.error` 原样弹出后端英文文案。
3. 后端广播 `agentStatusChanged` 终态 → `useTeamRunView.ts:296-305` 防抖后 `reconcile`（`GET run-state`）→ 新的 `slotWorkBySlot`（`:76-82`）。run / slot-work 事件走 `mergeSlotWork`（`:84-90`），同样每次新建。
4. `TeamPage.tsx:568-577` 生成新 Set → `TeamPermissionContext.tsx:66-80` 生成新 port → `:82-93` 生成新 context 值。
5. `prepareRuntimeSync` 变化，回到第 1 步，形成循环。同时，所有成员的 `useAcpConfigOptions` 实例都会因为 port 或 `prepareRuntime` 变化而重读。

失败的 POST 只会广播 `Starting` 和 `Failed`，不会广播 `Ready`（`service.rs:1475-1527`、`:1595-1601`、`:2209-2211`）。所以失败场景下 `sessionReady` 始终为 false。

# 附录六：ADR

- **Decision**：采用 A′，包括以下几项：
  - 消费方收窄依赖；
  - port 拆成两部分：只随 team 变化的函数，以及按内容变化的阻塞策略；
  - `useAcpConfigOptions` 改为按函数依赖 port；
  - Aion CLI 只在“挂载后 `sessionReady` 的上升沿、且尚未预热”时补一次预热；
  - 团队模式下静默挂载预热失败的 toast。
- **Drivers**：
  - 打断死循环，并消除正常场景下的放大；
  - pill 阻塞状态不过期，恢复后斜杠命令可用，且不引入自动重试；
  - 改动可测，不违反目录规则。
- **Alternatives considered**：A、A′ 的电平触发变体、B、C、D、E，否决理由见附录一。
- **Why chosen**：AC6（正常场景零重读）和 AC10（阻塞状态刷新）原本绑在同一个 port 身份上，只有拆开才能同时满足。重新预热信号只有做成“上升沿 + 尚未预热”，才能既恢复 AC9，又不新增自动重试，也不在健康打开时多发请求。
- **Consequences**：
  - 改 5 个源文件，其中包括共享 hook `useAcpConfigOptions`；
  - context 新增 `sessionReady`；
  - AionrsSendBox 多一个 effect；
  - 挂载期仍会有多次并发 ensure，但有进行中去重和上限 AC1 约束。
- **Follow-ups**（均不在本次范围，需用户决定）：
  - ACP 成员恢复后不会重新拉取斜杠命令（`useAcpMessage.ts:684-716` 的依赖是稳定的）；
